# Spotter extension design notes

## Overview

This is an ordinary extension of the pinned BluPe runner, in Operate mode. The visual authority remains `vendor/remote-yam/codex-runner/static/hosted.html`, `hosted.css`, and `hosted.js`. These notes describe the finished extension; they do not establish a replacement identity or promote local additions into a new design system. The project-root PRODUCT.md records confirmed product facts. No replacement DESIGN.md, direction contract, approved comp, or new-world quality bar applies to this pass.

The separate Spotter hosts preserve the live physical camera workspace, task conversation, compact task composer, and inherited run library. YAM1 pairs the frozen DreamZero policy with Spotter; Robo-house pairs hosted Dream-1 beta with Spotter. Each offers the same station policy alone as its baseline. Qwen is the backend supervisor; model execution location is a product fact, not a new visual rule. RPent remains future scope.

## Colors

The inherited console palette remains the source of truth: pale cream-green field (`--paper: #f3f4ef`), warm near-white surfaces (`--surface: #fffefa`), dark green text (`--ink: #203a30`), green actions (`--accent: #2d6048`), soft green selection (`--accent-soft: #eaf1e4`), muted text (`--muted: #59665f`), and quiet borders (`--line: #dce2d8`). These are the existing `.playgroundConsole` values in `hosted.css`, rather than new Spotter tokens.

The local readiness paragraph uses `#344454`. This is a scoped implementation value in `static/site.css`, not an additional normative palette role.

## Typography

Keep the runner's bundled Manrope and its existing `"Avenir Next", sans-serif` fallbacks. The console base is 14px; the extension inherits the wordmark, compact product label, heading hierarchy, and control typography. The new readiness paragraph is `.875rem` with a 1.5 line height, changing to `.8125rem` below 640px. It is supporting status copy, not a new heading style.

## Layout

The desktop camera workspace stays beside task chat, and mobile stacks the camera before chat. The inherited library and help sections retain their order. `static/site.css` limits the introduction and readiness paragraph to 75ch.

The separate host lacks the main site's composite media proxy. `spotter_yam/app.py` therefore selects the runner's fresh per-camera transport. The local multi-camera layout gives the overhead feed the full first row and places the two wrist views beneath it. Robo-house inherits the pinned runner's full-height overhead feed with gripper insets. These station-specific camera arrangements preserve the camera-first structure rather than replacing the global layout.

The terminal error state exposed a desktop sizing feedback loop: a long camera footer occupied 2213px and narrowed the camera to 177.8px. The scoped `static/site.css` fix limits the camera footer to a 180px block size at widths of 741px and above, with vertical scrolling and contained overscroll. Mobile retains natural document flow. The native camera fitter is unchanged; this is a local resilience fix, not a global spacing or component token.

## Elevation & Depth

The extension adds no shadow or elevation vocabulary. Existing borders, quiet surfaces, camera framing, and inherited transient overlays remain authoritative.

## Shapes

The extension adds no corner, border, or icon system. Controls, camera frames, composer, library cards, and dialogs inherit their existing shapes from the pinned runner.

## Components

- **Readiness status:** `static/site.js` reads the session extension and explains whether model services are configured. The paragraph remains a status region in the page generated by `spotter_yam/app.py`.
- **Station choice:** the inherited robot selector links the separate YAM1 and Robo-house services. The page title, policy identity, and available baseline follow the selected station.
- **Model choice:** retain Spotter and the matching policy alone: DreamZero on YAM1 or Dream-1 on Robo-house. Spotter is the default even where the incumbent runner would otherwise choose Dream automatically; explicit model selection remains available. Existing unrelated launch choices are hidden by the application extension.
- **Preparation state:** `spotter_yam/ui.py` applies a checked in-memory overlay to the pinned script. Spotter joins the inherited warmup treatment; preparation before a robot session exists shows no queue-place highlight and explains that the robot queue and run timer have not started. Robo-house readiness copy distinguishes Spotter preparation before the queue from the Dream-1 connection after the robot is reserved. Replacement-count checks fail visibly if the pinned source no longer matches. The vendored script itself is preserved.
- **Live views and task chat:** preserve the physical camera imagery, task prompt, stop action, and Spotter observations/repair decisions in the existing console structure.

## Do's and Don'ts

- **Do** inherit the native Manrope, cream-green ground, green controls, and camera-first responsive structure when extending this host.
- **Do** keep model preparation, robot queue admission, and active execution distinct in status copy.
- **Do** treat policy-alone runs as the explicit baseline and recorded outcomes as evidence only for the run they describe.
- **Don't** present preparation screenshots as completed physical Spotter execution or successful repair evidence.
- **Don't** canonize inherited reaction glyphs, historical media defects, or one-off extension values as future design rules.
